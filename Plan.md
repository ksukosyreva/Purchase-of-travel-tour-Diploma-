# План
## Перечень автоматизируемых сценариев.

### Для функции покупки дебетовой картой:
1. Одобренная банком покупка тура картой 4444 4444 4444 4441 "APPROVED" с валидными данными в форме -> сообщение "Успешно! Операция одобрена банком", в БД появляется запись "APPROVED".
2. Отказ банком при попытке покупки тура картой 4444 4444 4444 4442 "DECLINED" -> сообщение банка об отказе, в БД появляется запись "DECLINED".
3. Отказ банка по карте, которой нет в списке тестовых (например, 4444 4444 4444 4443), при попытке покупки тура -> сообщение банка об отказе, в БД появляется запись "DECLINED".
4. Форма оплаты не отправляется, если не заполнено любое из обязательных полей -> сообщение об ошибке.
5. Отправка формы оплаты тура картой 4444 4444 4444 4441 "APPROVED" с заполнением всех полей допустимыми граничными значениями -> форма отправляется; сообщение "Успешно! Операция одобрена банком", в БД появляется запись "APPROVED".
6. Отправка формы оплаты тура с заполнением всех полей недопустимыми граничными значениями -> поля подсвечиваются красным, сообщение об ошибке "Неверный формат".
7. Отправка формы оплаты тура с полями с неверным форматом (буквы, спец.символы, пробелы) -> все поля подчеркнуты красным, сообщение об ошибке "Неверный формат".
8. Попытка оплаты тура картой с истекшим сроком -> поле "год" подчеркнуто красным, сообщение об ошибке "Истёк срок действия карты".

## Используемые инструменты:
- Gradle - позволит подключать библиотеки, запускать тесты одной командой (./gradlew test), настраивать CI.
- JUnit Jupiter 5 - для упрощения написания тестов в том числе благодаря аннотациям для разных сценариев.
- Selenide - для взаимодействия с браузером и элементами web-интерфейса, удобного поиска элементов страницы, использования ожиданий и проверок.
- Docker - для взаимодействия с базами данных (MySQL, PostgreSQL), запуска эмулятора банковских сервисов, для использования Selenoid.
- Selenoid - для запуска браузеров в Docker-контейнерах, для взаимодействия с базами данных.
- Faker - для генерации тестовых данных в форме оплаты тура.
- Apache Commons DbUtils - для работы с JDBC, SQL-запросов и для проверки записей в БД после операций.
- REST-assured - для проверки ответов эмулятора банковских приложений.
- Gson - для парсинга JSON при работе с API.
- SLF4J - для логирования, которое поможет лучше понимать проблемы в автотесте и также логи можно прикрепить к отчету в Allure.
- Lombok - для упрощения и сокращения кода при использовании PageObjects.
- Allure - для создания наглядного визуального отчёта о проведенных тестах.
- СУБД: MySQL, PostgreSQL (для проверки данных в БД)

## Перечень и описание возможных рисков при автоматизации:
- Если приложение aqa-shop.jar не запускается или падает во время выполнения, автотесты не смогут выполниться или будут падать с ошибками подключения.
  Это может быть вызвано конфликтом портов, ошибками в конфигурации, недоступностью БД или эмулятора.
- Если не очищать БД перед/после тестов, накапливаются данные, что приводит к конфликтам (например, при создании пользователя с тем же логином),
  искажению результатов проверок и каскадным падениям тестов. Также приложение может не запуститься, если оно само пытается создать уже существующие данные.
- Если эмулятор (gate-simulator) отвечает неверно (например, DECLINED вместо APPROVED), тесты будут падать. Можно решить, что баг в приложении, хотя проблема в эмуляторе. Это увеличивает время на поиск причины.
- Если разработчики изменят селекторы, тесты будут падать из-за невозможности найти элементы (или находить не те элементы), что приводит к ложным результатам и требует обновления Page Object.
- При обновлении приложения может потребоваться доработка Page Object, SQL-запросов, тестовых данных и самих сценариев. Это увеличивает трудозатраты на поддержку.
- Если использовать одни и те же тестовые данные, снижается вероятность обнаружения дефектов с другими данными. Со временем одни и те же тесты перестают находить новые баги (эффект пестицида). Требуется генерация уникальных данных (Faker).
- Если логи и Allure-отчёты не сохраняются или не генерируются, невозможно проанализировать причины падений и подготовить Summary/Report. Это риск срыва сдачи итоговой документации.
- Если CI настроен неверно или в репозитории отсутствуют необходимые файлы, проверяющий не сможет запустить тесты. Это критический риск для сдачи диплома.
- Если тесты не изолированы, они влияют друг на друга. Например, первый тест перевёл средства с карты, и на втором тесте денег уже нет — он падает, хотя приложение работает верно. Другие примеры: незакрытая сессия, неудалённые данные в БД, сохранённые cookies. Это приводит к каскадным падениям и ложной диагностике.
**личные риски**:
- Ограниченное количество рабочих часов в день (4-6 часов) из-за внешних обстоятельств.
